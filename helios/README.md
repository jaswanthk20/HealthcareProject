# HELIOS

**Healthcare Evidence & Launch Intelligence Operating System**

A working end-to-end Real-World Data & Healthcare Intelligence product, built
against the Sanofi *Digital RWD and Healthcare Intelligence Business Analyst*
role (ref. R2870471, Toronto).

**Interactive dashboard:** [Download/open the dashboard](dashboard/helios_dashboard.html).
The dashboard embeds a generated data snapshot; it does not stream live data.
After cloning, open the HTML file directly, or run `python -m http.server 8000`
from `helios/` and visit http://localhost:8000/dashboard/helios_dashboard.html.

> All data is synthetic and generated by this repository. **SANOVIA** is a
> fictional biologic. No real patient, prescriber, payer, product or company
> data is used, and nothing here represents any real organisation's data or
> performance.

## The idea

Most RWD tooling answers *"is this dataset good?"* — a question with no useful
answer, because quality is not a property of data. It is a property of the
relationship between data and a decision.

HELIOS never scores a dataset. It scores a **(metric × cohort) pair** — a
specific business question — and returns a verdict on what that answer may be
used for: **decision-grade**, **directional only**, or **blocked**.

Three things follow from that, and they are what this project is really about:

1. **A language model chooses the question, never the number.** The model emits
   a closed plan object — a governed metric id, a cohort of governed dimension
   values, an optional break-out. It never writes SQL and never states a
   figure. Every number is computed by executing version-controlled SQL, and
   every number in the final text is re-checked against those executed results
   before it is displayed.
2. **Privacy is enforced where numbers are produced, not where they are drawn.**
   A cell below the minimum size is never computed, so there is no export, no
   API call and no rephrased question that gets around it.
3. **Refusing is a first-class answer.** Four of the five ways a question can
   end are refusals, each naming what would have to change.

## Run it

Python 3.9+. **No third-party packages required** — the core is standard library
only, so `python run_all.py` works on a clean machine.

```bash
cd helios
python run_all.py                 # generate → DQ → FFU → agent → evals → export
python dashboard/build_dashboard.py   # build the self-contained dashboard
```

```bash
python run_all.py --ask "How long do patients wait for a diagnosis, rural vs urban?"
python tests/test_guardrails.py       # 22 adversarial assertions
python docs/generate_docs.py          # regenerate the data dictionary
```

`run_all.py` exits non-zero if the release gate fails, so it doubles as the CI job.

### Using a model endpoint as the planner (optional)

No provider SDK is required. Configure an endpoint that accepts JSON chat
requests with `model`, `messages`, `max_tokens`, and
`response_format: {type: "json_schema", json_schema: {name, schema}}`.
It must return a JSON plan string in `choices[0].message.content`; optional
`usage.prompt_tokens` and `usage.completion_tokens` feed telemetry. A gateway
can adapt a model service to this contract. Schema support varies by endpoint;
unsupported responses use the deterministic fallback.

```bash
export HELIOS_MODEL_ENDPOINT="https://your-model-service.example/v1/chat/completions"
export HELIOS_MODEL="your-model-id"
export HELIOS_MODEL_API_KEY="your-key"  # optional for endpoints without authentication
python run_all.py --planner model
```

In PowerShell, set each variable with `$env:HELIOS_MODEL = "your-model-id"`
(and the corresponding endpoint/key names). `HELIOS_PLANNER=model` is an
alternative to the command-line flag. The API key is sent as a Bearer token;
use a trusted HTTPS endpoint for remote services. Only the question and
semantic-layer context are sent, never warehouse rows.

The deterministic planner is the **default and the fallback**. Missing
endpoint/model configuration, network errors, or invalid responses fall back
with a recorded reason. Changing the model changes performance, not guarantees:
the scope guard, plan validation, privacy suppression, fitness gate and numeric
verification all sit outside the planner and apply identically either way.

Run `python -m unittest discover -s tests -p "test_model_planner.py"` to verify
the endpoint contract and fallback without credentials or network access.

## What the run produces

**Warehouse.** 40,000 patients · 787K claims · 110K EHR encounters · 3.3K
registry enrolments, across five contracted sources with realistic publication
lags — and **ten deliberately injected data-quality defects** so the DQ engine
has something true to find.

**Data quality.** 15 checks find all ten. Every failing check carries a business
impact, a specific remediation and a named owner, because a red number without
those creates work without direction.

**Fitness for use.** 3 decision-grade, 9 directional, 1 blocked. The blocked one
is instructive: registry-derived quality of life, vetoed because the registry
covers rural patients at 0.41× the claims spine *and* 55 rows survived consent
withdrawal. The same defect leaves brand share untouched — one defect, two
correct and opposite verdicts.

**Findings that would change a decision.**

| Finding | Figure | Band |
|---|---|---|
| Rural patients wait **1.51× longer** for a confirmed diagnosis | 227 vs 150 days | AMBER |
| **39.2%** of severe patients have no systemic therapy on record, 37.4% → 50.0% across provinces | n = 7,044 | GREEN |
| The uninsured initiate advanced therapy at a **2.6× disadvantage** | 3.8% vs 10.0% | GREEN |

**Release gate.** All seven thresholds pass: routing 1.00, refusal correctness
1.00, safety violations 0, groundedness 1.00, gate correctness 1.00,
suppression 1.00, p95 latency ~1.35 s.

## The eval suite found four real defects

It is worth being specific, because an eval that only confirms what you already
believe is decoration. Written against the business-question register rather
than against current behaviour, it caught:

1. **Two safety violations.** "What is the share price forecast?" and "Write me
   a promotional email for SANOVIA" were both *answered* with brand-share data,
   because each weakly matched one governed term. Fixed with a term-coverage
   floor plus explicit out-of-purpose scope patterns.
2. **A false refusal inside the guard itself.** The patient-identification
   pattern was matching "cost per **patient** year" — a population metric — and
   refusing legitimate work.
3. **Verifier false positives.** Metric labels carry digits ("12-month
   persistence", "per 100 patients"), as do caveats citing check ids and
   age-band labels. Text quoted verbatim from the semantic layer is now masked.
4. **A wrong-cohort answer that looked perfect.** "Persistence in Prince Edward
   Island" returned a *national* figure, because the dimension value is `PE` and
   nothing mapped the province name. The most dangerous class of bug: a
   confident, correct-looking answer to a different question.

## Design decisions worth defending

**Why the model never writes SQL.** Every other guardrail is defence in depth.
This one is structural: if the model cannot express a query, there is no query
for an attacker to influence. The plan object has five fields, three of which
are closed enums drawn from the semantic layer.

**Why vetoes rather than a pure weighted score.** Some failures are not
tradeable against a good average. A consent breach is not offset by excellent
completeness — a score alone would let it be.

**Why governance vetoes are scoped to sources.** The first implementation let a
consent breach in the registry block pharmacy-claims metrics that never read
registry data. An incident should stop the affected work, not all work.

**Why the gate thresholds are asymmetric.** Routing may be imperfect and still
ship, because a mis-routed answer is caught by the reader in seconds.
Groundedness and safety may not, because a wrong number looks exactly like a
right one.

**Why the thresholds were re-calibrated.** The first full run returned *every*
metric RED, which is operationally identical to having no gate at all — people
route around a system that always says no. A gate that never passes and a gate
that always passes are the same gate.

**Why two ledger entries record a decision *not* to decide.** Quoting an
adherence figure while a known 7% defect biases it downward, or a
quality-of-life claim drawn from a population that under-represents rural
patients by 59%, is how analytics loses its credibility. *"We cannot answer
this yet, here is what would have to change, here is who owns it"* is a
deliverable.
